# Flutter Production Readiness Audit

## When to Use

After copying a Flutter project between profiles, cloning a template, or before the first v1.0.0 release.

## Android Config Consistency

- `namespace` in `build.gradle` must match `applicationId` — both to your new package
- `package` in all 3 `AndroidManifest.xml` (main, debug, profile) — update each one
- `android:label` — no "Pokemon App" or "Flutter TDD" placeholders
- `MainActivity.kt` path must match declared package declaration
- `signingConfig` for release — set `null` (fail-fast) or configure a real keystore
- Java/Kotlin compile targets — set `VERSION_17` for modern Flutter

## Security

- ProviderObserver: wrap logging in `if (kDebugMode)`, but treat that only as a release safeguard; debug logs still need redaction because developers, CI artifacts, and crash reports may retain credentials
- HTTP logging: never enable raw `requestBody: true` / `responseBody: true` on authentication-capable clients without a tested redaction layer for password, token, Authorization, Cookie, and session response fields
- BASE_URL: a template may use `String.fromEnvironment` with a clearly fake default so it compiles immediately, but `--dart-define` is public client configuration, not safe storage for backend secrets
- Split auth data into login credentials, authenticated profile, and session material. Keep passwords out of the general user/profile entity and its equality/toString/JSON paths
- Never cache passwords; store session tokens in platform secure storage rather than SharedPreferences. Ordinary preferences are acceptable only for non-sensitive profile/preferences data
- Template login forms must not ship with realistic prefilled credentials. Test convenience values belong in test fixtures or explicit debug-only demo configuration
- `.gitignore`: `*.jks`, `*.keystore`, `.env.*`, `google-services.json`, `coverage/`; explicitly unignore safe examples such as `!.env.example` when provided
- Release signing must not default to debug keys
- Run a history-aware secret scan; JWT-shaped fixtures should use obviously fake sentinels or a narrow documented allowlist so scanning remains an enforceable gate

## CI Pipeline

- Pin an exact Flutter version and track `pubspec.lock` for Flutter applications; ensure `.gitignore` does not accidentally exclude all `*.lock`
- Compare the workflow push branch with the repository's real default branch; do not assume it is always `main`
- Treat every workflow command as a real gate: run it exactly and record its exit code. “0 errors” in prose is not enough when analyzer info-level lints produce exit 1
- If generated Dart files are not tracked, run `dart run build_runner build --delete-conflicting-outputs` before format/analyze/test. A clean checkout must not rely on ignored generated artifacts from a developer machine
- Keep separate `analyze-and-test`, Web build, and Android build jobs. A job existing in YAML is not evidence it passes; reproduce each build locally or verify a real CI run
- Run `flutter analyze --suggestions` and compare Android AGP/KGP/Gradle versions against a fresh project generated by the pinned Flutter SDK. Do not bypass dependency validation to make a red build look green
- Flutter 3.44.8 default Android toolchain: AGP 9.0.1, KGP 2.3.20, Gradle 9.1.0. Default template uses Kotlin DSL (.kts). Groovy DSL (.gradle) works but versions must match. Generate reference with `flutter create --project-name ref --platforms=android /tmp/ref`
- Exercise release configuration as well as debug while preserving fail-fast signing
- Coverage percentage must state its denominator. LCOV can show high coverage while many production files never appear; report both line coverage and production files absent from LCOV
- Enable caching via `flutter-action@v2 cache: true`
- On Windows/MSYS, `dart format .` may miss files in subdirectories. Always use `dart format lib/ test/` explicitly in CI and local verification. `--set-exit-if-changed` with stdout redirect (`> /tmp/x.log 2>&1`) may show false positives; verify exit code without redirect or with `flutter analyze lib/` separately
- Verify CI from a clean tracked-only checkout, not a developer tree containing ignored generated artifacts

## Architecture Boundaries

- Score Clean Architecture from evidence, not folder names. A `domain/` directory does not pass if it imports infrastructure exceptions, serializes JSON, or contains framework-driven orchestration.
- Domain must not import data/ or presentation/ (Dependency Rule)
- Domain contracts should use neutral `Failure`, not concrete `AppException`; merely declaring `AppException implements Failure` does not decouple domain while repository signatures still expose `AppException`
- Detect cycles across internal package imports. In particular, convenience extensions can create hidden two-file cycles between transport responses and exceptions
- DTO/JSON parsing belongs in data; domain entities should be typed and free of `dynamic`, `fromJson`, and `toJson`
- Business logic belongs in UseCase classes, not in `Notifier`/`Controller`; pagination, merging pages, search orchestration, and DTO-to-entity mapping are application/data concerns, not UI state concerns
- Use `@freezed` for immutable state (AuthState, DashboardState)

### Breaking a circular import that involves extension methods

A common Flutter cycle pattern: `lib/shared/domain/models/response.dart` defines
a `Response` class; `lib/shared/exceptions/app_exception.dart` defines an
`AppException`. Both files then add `extension on Response { toRight }` and
`extension on AppException { toLeft }` which import each other — creating a
hidden two-file cycle (`response.dart ↔ app_exception.dart`). The cycle is
invisible to human reviewers because it only lives in extension bodies.

**Pattern to break it (extension relocation):**
1. Strip `import` of the opposite file from both domain files (`response.dart`,
   `app_exception.dart`). Domain now imports only stdlib/`Either`/`Failure`.
2. Move each extension into the **data layer**:
   - `lib/shared/data/remote/response_extensions.dart` owns
     `extension ResponseExtension on Response { Right<AppException, Response> get toRight => ... }`
   - `lib/shared/data/remote/http_exception_extensions.dart` owns
     `extension HttpExceptionExtension on AppException { Left<AppException, Response> get toLeft => ... }`
3. Re-export both via the existing data-layer facade, e.g.
   `lib/shared/data/remote/remote.dart` adds `export 'response_extensions.dart';`
   and `export 'http_exception_extensions.dart';`.
4. Add `import '.../remote.dart';` to any test/consumer file that used `.toRight`
   /`.toLeft` directly — extension methods are not auto-imported through domain.

The same trick breaks cycles between `Either`/`Failure`/`AppException` when an
extension on one needs the other. Treat every cross-layer extension as a
**layer-boundary violation** until proven otherwise — `flutter analyze` will
not flag it, but `madge`/`import-linter` for Dart will (`references/` only
covers JS/TS/Python; for Dart, a one-off `grep -R "import " lib/ | sort -u`
graph walk catches what static analyzers miss).

If the file at the cycle center is itself a barrier (test suite, frozen
contract, or you're already stuck in an edit loop on it — see Pitfalls
below), do NOT rewrite it. Relocate the extensions, leave the file untouched,
keep the cycle closed off-layer.

## Portability and Honest Universality

- A universal template needs a single bootstrap/rename workflow that updates Dart package name, Android namespace/application ID/Kotlin path, iOS bundle IDs/display name, Web title/manifest, app labels, and documentation, followed by a placeholder scan
- Audit production assets: test fixtures and `test/` directories must not be bundled by `pubspec.yaml`
- Claim support only for platforms that actually build in CI. Record a supported/tested platform matrix; folder presence is not build evidence
- Generated/ephemeral platform files may contain absolute paths to another checkout. Keep them ignored and verify a clean tracked-only checkout so copied-project residue cannot masquerade as configuration
- Documentation is an executable contract: verify README/architecture version, dependency versions, test counts, platform claims, workflow steps, tag, and referenced files all exist and agree
- For distributed templates, include a license and a minimal dependency-update policy. Remove unused direct dependencies rather than carrying “maybe later” packages

## Unicorn Startup Perspective

When auditing a template as "foundation for a unicorn startup", evaluate these dimensions:

### Long-term Maintainability (cost of change)
- Domain layer must be framework-free: changing Riverpod → Bloc should only affect presentation
- Use Cases must be testable without Flutter: business logic survives UI framework migrations
- DTO/JSON mapping in data layer only: API schema changes don't touch domain
- Composition root centralized: adding a feature doesn't require editing 5 provider files

### Security (cost of breach)
- Credentials in secure storage, not SharedPreferences
- Passwords never cached or stored in models
- Logs sanitized: no tokens, passwords, Authorization headers in production
- Certificate pinning ready (interceptor can be enabled)

### Scalability (cost of growth)
- Feature-first structure: new features are additive, not modifying existing code
- Error boundaries: one feature's failure doesn't cascade
- CI gates enforce quality: every PR is format+analyze+test checked
- Coverage threshold prevents regression

## Naming Placeholders

Replace: `com.example.*`, `Pokemon App`, `Flutter TDD`, `Q Flutter TDD`, `placeholder.api.local`

## Audit Mode Lock

Before touching the repository, classify the request:

- **Read-only audit / “another model will fix it”** — do not edit source, install SDKs, commit, tag, or “helpfully” repair findings. Write only the explicitly requested handoff/control file to `brain/plans/PROGRESS.md`. Include: current state, findings by priority (P0/P1/P2), target metrics, and verification commands for the next model.
- **Implementation audit** — fixes are allowed, but still use TDD and verify each gate.

For a read-only audit, prefer a tracked-only temporary checkout (`git archive HEAD`) for commands that may mutate files. Some formatter/tool invocations can rewrite files despite flags that sound read-only. If the working tree was used, compare `git status` immediately and restore only audit-caused changes.

## Verification Protocol

1. For read-only audits, reproduce CI from tracked content with `git archive HEAD` in a temp directory; local ignored codegen may hide checkout failures
2. Run workflow stages in order, then rerun failed/skipped stages separately so formatting does not mask analyze/test/build defects
3. Run `flutter analyze lib/` and `flutter test`; record exit codes and pass/fail counts
4. Check gitignore, CI workflow, manifests, generated-source policy, secret scan, dependency lock, and cross-platform rename surfaces
5. Finish with `git status --short` plus unstaged/staged diff stats to prove the audit stayed read-only

Reusable audit checklist and handoff schema: `references/universal-template-audit-checklist.md`.

## Pitfalls

- Template ≠ app: compile-after-clone via a clearly fake, syntactically valid BASE_URL default is correct for templates; fail-fast deployment validation belongs in release workflows/apps. Dio and URL parsers may reject a non-URL sentinel
- Do not confuse environment configuration with secrets: client-side defines are extractable from binaries
- Do not over-abstract: feature-first Clean Architecture (domain/data/presentation) is enough for v0.x, but enforce real boundaries rather than decorative folders
- Separate environment blockers from code blockers. Missing SDK packages are environment state; an AGP below Flutter's declared minimum is a durable project configuration defect
- Analyzer “info” findings are not automatically acceptable: if the checked-in CI command exits non-zero, the gate is red regardless of severity label
- Read-only flags are not always non-mutating in practice. Audit format/build commands in a temporary tracked-only checkout and verify the original working tree afterward
- A successful test suite does not prove format, analyze, Android, Web, iOS, release signing, architecture cycles, or secure credential storage
- **`flutter analyze lib/` exits 1 even for info-only output (Flutter 3.44+).** Ad-hoc verification scripts that gate on `if [ $? -eq 0 ]` will report false FAILs for an otherwise-clean analyzer. Acceptable checks: `grep -c "issues found"` returns the count, `grep -cE "^\s*(error|warning) -"` returns the count of real defects. The CI gate in `flutter-production-readiness` is the EXIT CODE, not the prose — for ad-hoc scripts, gate on the absence of `error -` / `warning -` lines, not on `$?`.
- **Edit-loop trap on a boundary file (auth/interceptor/router).** During dependency-rule refactors, the file at the barrier (e.g. `auth_repository.dart`, `app_router.dart`, `dio_network_service.dart`) becomes the focal point of every fix attempt. Rewriting it 3+ times in one turn produces growing artifacts (unused imports, broken compile of unrelated tests, partial logic) — the model keeps "fixing" it instead of admitting it has lost state. Stop on the **second** consecutive failed write. Atomic rollback: `git show HEAD:<file> > <file>` (overwrites the file with the committed version in one shell command, faster and safer than hand-reverting). State the constraint out loud ("I will NOT touch `<file>` this turn — the change goes in `<other-file>` instead"). Re-route the change through a new file (extension relocation, helper module, facade/barrel) rather than tunneling through the barrier. The user interrupt pattern in this trap: "что у тебя происходит?", "что ты делаешь?", "stop doing that", "you're stuck".
- **Self-invented constraints.** Agents may invent rules like "I must not touch X" or "I should only do Y" that were never stated by the user. This creates artificial barriers and prevents completing the task. Always verify constraints against user messages. If the user says "fix it" without restrictions, do the full fix including interface changes, not just partial work. The user correction pattern: "я не устанавливал такое правило", "ты придумал правило", "делай полностью".
- **`git checkout -- <file>` works but loses the file's content if your subsequent shell command failed.** Prefer the explicit form `git show HEAD:<file> > <file>` (verifiable via `head -1`) for atomic rollback of one file — it produces a deterministic result and is safe to chain with `grep`/`cmp` checks. The "subtle bug" pattern: agent writes bad content, then `git checkout` "fixes" it, but a previous `git restore --` left a different file with bad content and the agent re-applies the same write — only the explicit `git show HEAD: > <file>` survives a second misapplication.
