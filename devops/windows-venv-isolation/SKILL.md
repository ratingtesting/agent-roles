# Isolated Python venvs on Windows + Hermes agent

When you work inside the Hermes desktop app on Windows, two environment traps
silently corrupt any project venv you create. Both come from the agent's own
runtime, not from your project.

## Trap 1 — venv "base" points at the Hermes agent venv
The shell's `python` on PATH is often the Hermes agent's *temporary* venv
(e.g. `/tmp/c4aivenv` or `.../hermes-agent/venv`). Running `python -m venv .venv`
writes that path into `.venv/pyvenv.cfg` as `executable=` / `home=`. Result:
the project venv resolves its `site-packages` to the agent venv, not to
`.venv/Lib/site-packages`.

Symptom: packages import fine for the agent, but the project's
`.venv/Scripts/python` pulls the agent's package versions (e.g.
`tokenizers 0.23.1` instead of the project's `0.22.2`), causing
`ImportError: ... required, found ...` at startup.

**Fix:** create the venv with an explicit, stable interpreter — the uv-managed
cpython the host actually uses — NOT whatever `python` resolves to:
```
"C:\Users\<user>\AppData\Roaming\uv\python\cpython-3.11.15-windows-x86_64-none\python.exe" -m venv .venv
```
Verify: `.venv/pyvenv.cfg` must show `home = .../uv/python/cpython-...` and
`executable = .../uv/python/cpython-.../python.exe` (NOT a hermes-agent path).
Then confirm runtime isolation:
```
env -u PYTHONPATH .venv/Scripts/python -c "import sys; print(sys.prefix)"
```
→ must print `...\your-project\.venv`.

**Keep the Python version the user already had.** Recreating a venv is NOT a
reason to upgrade Python. Reuse the existing interpreter path; do not select or
install a newer release. (User explicitly objected to a version change during a
venv repair — treat the version as fixed unless told otherwise.)

## Trap 2 — PYTHONPATH injection from the Hermes process
The Hermes process exports:
```
PYTHONPATH=C:\\Users\\<user>\\AppData\\Local\\hermes\\hermes-agent;C:\\Users\\<user>\\AppData\\Local\\hermes\\hermes-agent\\venv\\Lib\\site-packages
```
This makes BOTH the project's `python` AND `pip` see the agent's packages first.
Two nasty consequences:
1. `pip install X` prints `Requirement already satisfied: X in
   .../hermes-agent/venv/...` and SKIPS installing X into your `.venv`. The
   package is then missing from the project venv.
2. Importing the project resolves transitive deps (requests, tqdm, yaml, regex,
   typing_extensions, joblib, httpx, pydantic_settings, h2, jinja2, uvicorn,
   pytest, ...) from the agent venv, often at the WRONG version, producing
   `ImportError: ... required, found ...` or `No module named ...`.

**Fix — always strip PYTHONPATH for project commands:**
- bash / MSYS terminal: prefix every command with `env -u PYTHONPATH`:
  ```
  env -u PYTHONPATH .venv/Scripts/pip install <pkgs>
  env -u PYTHONPATH .venv/Scripts/python -m uvicorn <app> --factory ...
  env -u PYTHONPATH .venv/Scripts/python -m pytest tests/unit
  ```
- `run_server.bat` / autostart scripts: first line `set PYTHONPATH=` (then
  `cd /d ...`). Do NOT rely on the global env; the batch file must clear it
  itself, otherwise the autostarted server inherits the leak.

### Trap 2a — .exe launchers and `PYTHONPATH=` vs `env -u PYTHONPATH`

Tools installed in THEIR OWN venv (not your project venv) also break:

| Tool | Installed via | Symptom |
|---|---|---|
| **SkillSpector** | `uv tool install skillspector` | `ImportError: ... pydantic_core._pydantic_core` |
| **OpenHands agent-server** | `pip install openhands` in dedicated `.venv` | Same pydantic_core crash |
| **Any .exe-launched tool** using pydantic | Any method | Hermes venv's pydantic version shadows the tool's |

**Why `env -u PYTHONPATH` doesn't always work for .exe wrappers:**

Python `.exe` launchers (generated by pip entry points) re-append the hosting
venv's site-packages LAST in `sys.path` — but if `PYTHONPATH` is SET (even to
empty string `PYTHONPATH=`), the *launcher's* resolution still picks up
`PYTHONPATH` entries before the hosting venv's own packages. Result: pydantic
from the Hermes venv (`...hermes-agent/venv/Lib/site-packages`) loads first,
causing `ImportError: cannot import name '...' from 'pydantic_core._pydantic_core'`
— the pydantic versions are incompatible.

**Trap 2b — Electron Desktop Apps (Agent Canvas)**

Desktop apps bundled as Electron apps (e.g. **Agent Canvas / OpenHands UI**)
also inherit PYTHONPATH from the Hermes process, even though they are NOT
Python tools themselves. The Electron main process starts a Python
agent-server via uvx (`uvicorn`). When PYTHONPATH is set, the uvx-spawned
uvicorn loads pydantic/pydantic_core from the Hermes venv instead of the
uv-managed cache, producing `ModuleNotFoundError: No module named 'pydantic_core._pydantic_core'`.

**Symptom:** Agent Canvas starts, the agent-server process crashes immediately,
the Electron app reports "Agent server never came up."

**Fix — strip PYTHONPATH before launching the Electron app:**

```bash
# PowerShell:
$env:PYTHONPATH = ''
Start-Process -FilePath 'C:\path\to\Agent Canvas.exe'

# bash/git-bash:
export PYTHONPATH=""
"path/to/Agent Canvas.exe"
```

Note: the Electron app spawns multiple child processes (ingress proxy via
Node.js, agent-server via uvx). PYTHONPATH must be cleared in the PARENT
process environment before launch; setting it inside the Electron app's
spawned shells is too late.

**Known limitation:** on some Windows 11 machines `localhost` resolves to `::1`
(IPv6) but the agent-server only binds to `127.0.0.1` (IPv4), causing the
ingress proxy to fail with `ECONNREFUSED ::1:18000`. See
`references/agent-canvas-setup.md` for the patch fix.

**Onboarding API key:** after the backend starts, the Electron app shows
a 3-step wizard. Step 3 ("Check your backend") may ask for an API key —
this is the auto-generated session API key found in the page HTML.
See `references/agent-canvas-setup.md` → "Onboarding wizard" for details.

**Fix — for .exe-based tools, use the venv's python directly:**

```bash
# BAD — even with PYTHONPATH=, the .exe launcher may still see hermes packages:
PYTHONPATH= skillspector --version

# GOOD — bypass the .exe entirely, use python -m from the tool's own venv:
PYTHONPATH= /path/to/tool/.venv/Scripts/python -m skillspector --version
PYTHONPATH= /c/Projects/lazy-unicorn/openhands/.venv/Scripts/python -m openhands.agent_server
```

For `uv tool install`-ed tools specifically, they live under
`%APPDATA%\local\uv\data\tools\<tool-name>\venv\Scripts\` or similar, and you
can run them as `uv tool run --isolated <tool>` which strips PYTHONPATH entirely.

**Detecting this leak:** the signature is a pydantic import error (or any
error that mentions `hermes-agent/venv/Lib/site-packages` in the traceback)
when running a tool that has its *own* venv with pydantic installed. Grep
the traceback for `hermes-agent` — if it appears, PYTHONPATH leaked.

## Verification checklist (run before declaring the server "works")
1. `env -u PYTHONPATH .venv/Scripts/python -c "import sys; print(sys.prefix); print([p for p in sys.path if 'hermes' in p])"`
   → prefix == project `.venv`, and the Hermes list is empty.
2. `env -u PYTHONPATH .venv/Scripts/pip list` shows the project's own packages
   (not agent versions).
3. Start the server WITH `env -u PYTHONPATH` and hit `/healthz`, `/v1/models`,
   and a real embedding/request; assert the default model loads and the
   embedding dimension is correct.
4. Run the project's unit tests with `env -u PYTHONPATH .venv/Scripts/python -m pytest ...`.

## Pitfalls
- Do not trust a handoff prompt that asserts "the server is running / routes are
  duplicated / config X is present / versions are Y". Live-verify each claim;
  in practice the prompt's stated state was wrong on every single point.
- `pip install` reporting "Successfully installed" for the top-level package is
  NOT proof transitive deps landed in the project venv. Re-run the import and
  watch for the next missing module; install each with `env -u PYTHONPATH`.
- Gradio/UI is optional; if `jinja2` is missing the API still works (UI just
  gets disabled). Don't block an embedding-only server on the UI.
- `set PYTHONPATH=` in a `.bat` and `env -u PYTHONPATH` in bash are the SAME
  fix expressed for each shell — apply both where relevant.
- Patching a broken venv: when `pip` refuses to uninstall a package "outside
  environment" (because it thinks the install lives in the agent venv), delete
  the package directory manually (`rm -rf .venv/Lib/site-packages/<pkg>*`) then
  `pip install --no-deps <pkg>==<ver>` with `env -u PYTHONPATH`.
