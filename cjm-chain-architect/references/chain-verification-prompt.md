# Композиция промпта для проверки JSON цепочек мощной моделью

Когда нужен промпт, которым МОЖНАЯ модель (вне роя) проверяет `ALL_CHAINS*.json` на соответствие
канону CJM/JTBD/TOFU/MOFU/BOFU — промпт НЕЛЬЗЯ делать «куцым» (замечание владельца, дважды).
Промпт обязан нести полный контекст, ссылки на файлы и ПРОТОКОЛ исправлений, иначе модель
прочитает JSON как «список строк» и не поймёт, зачем это и что делать с дефектами.

## Что ОБЯЗАТЕЛЬНО входит (минимум)

1. **ЗАЧЕМ (цель проекта)** — первый блок, до любых правил. Частный риелтор по воронке доводит
   посетителя до ПОКУПКИ гайда ИЛИ УСЛУГИ сопровождения. Сверх-цель каждой цепочки — продажа
   гайда (правильного направления!) или заказ услуги. Цепочка без выхода на продажу — недоработка.
   Без этого модель не понимает критерий №1 и «проверяет форму», а не «помогает продавать».

2. **4 гайда + зачем каждый** — по одному на направление: купить/продать/сдать/снять.
   Проверка `chain.guide` ↔ `guide_id` в ядре: гайд покупателя ≠ продавца ≠ сдать ≠ снять.

3. **Пути к файлам** — JSON цепочек И ЯДРО (`CORE_JTBD_v*_ACTIVE.csv`). Из ядра — колонки
   `phrase / guide_id / route / funnel_v2 / cjm_stage / v6_direction / count / chain_leaf_ready /
   chain_id_leaf`. Ядро для СВЕРКИ: реальна ли фраза, та ли стадия/направление, та ли цепочка её покрывает.

4. **Ссылка на задание воркера** (`*task_body*.txt`) — там запреты Г1–Г10 и структура, по которым
   строились цепочки. Промпт должен говорить модели «это эталон требований».

5. **Правила проверки «критерий + КАК ИСПРАВИТЬ»** — каждый блок с явным исправлением, а не
   только констатация дефекта. Три действия: A = RETURNED в ядро (фраза неверна по существу),
   B = СИНТЕЗ звена (фразы нет, но звено нужно — с `synth_reason` + цитатой гайда),
   C = пересборка (фразы верны, структура сломана). Это канон §2.7 + §1.2k.

6. **Жёсткие правила гео и вида строения** (Г2–Г5): МО ≠ лист московской цепочки; Новая Москва =
   район Москвы; Зеленоград = Москва; переход Москва↔МО запрещён; районы только наверх; тип дома
   (нет 30 фраз — нет ветки по виду, все виды в листья); нельзя склеивать виды в «один фонд».

7. **Машинный гейт G1–G12** (из `scripts/cjm_gate.py`) — таблицей, как источник, а не «свод правил».

8. **Статистика для отчёта** — 8–9 метрик: по направлениям, по правилам, судьба фраз (RETURNED /
   синтез / пересборка), монетизация (сколько доводят до продажи), гео-нарушения, покрытие ядра
   (chain_leaf_ready=yes, число и %), топ-3 эталона / топ-5 худших, % готовых к публикации.

## Форма ответа промпта (строго)
1. Резюме: N / X PASS / Y FAIL / Z PARTIAL / W с проблемой монетизации.
2. Таблица дефектов: chain_id | уровень | правило (№ или G) | что не так | ДЕЙСТВИЕ (A/B/C) | как исправить.
3. Блок монетизации (не доводят до продажи + рекомендации).
4. Блок связности (сломанные цепочки, переходы/скачки).
5. Блок гео и вида строения. 6. Блок поломок: списки RETURNED (с причиной) / СИНТЕЗ (с обоснованием) / ПЕРЕСБОРОК.
7. Статистика. 8. Топ-3 эталона + топ-5 худших.

## Ошибка прошлых версий (не повторять)
- Промпт без цели/файла ядра = «куцый»: модель не понимает, зачем это, и не проверяет продажу.
- Промпт со «сводом правил» без привязки к параграфам скилла = нЕ канон, «другая точка зрения».
- Промпт, который только констатирует дефект без действия A/B/C = бесполезен: аудит должен давать
  ПЛАН, после которого цепочки начинают продавать.
- Рабочий пример итогового промпта: `11_cjm_chains/ПРОМПТ_ПРОВЕРКА_JSON_v3.md` (эталон композиции).
