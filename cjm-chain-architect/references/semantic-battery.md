# Семантическая батарея — проверки, которых НЕТ в гейте G1–G12

Гейт `cjm_gate.py` не проверяет гео, смену намерения, развилки и ширину ствола по count.
После каждого GREEN-файла прогонять `scripts/semantic_battery.py` — он печатает конфликты;
нулевой вывод = батарея чиста. Владельцем потребовано дважды (аудит v2 и v3).

## 1. Гео-микс: Москва ↔ Московская область внутри одной ветки

Классифицировать КАЖДУЮ фразу узла; ветка с обоими классами = дефект.

**Москва (не путать с МО!):** улицы/метро с названием МО-города — «коломенская»,
«клинская», «щёлковская», «серпуховская», «орехово борисово», «воскресенское»
(поселение НМТ), «дмитровский район» — двусмыслен, смотреть контекст «москва».
Новая Москва, Троицк, Щербинка, Зеленоград = Москва.

**МО:** области/подмосковье, города с точным вхождением: Люберцы, Ногинск,
Красногорск, Домодедово, Мытищи, Балашиха, Подольск, Одинцово, Электросталь,
Коломна, Клин (отдельное слово), Серпухов (не «серпуховская»), Воскресенск (город,
не «воскресенское»), Химки, Долгопрудный, «город Московский» (посёлок в ТиНАО-округе
Некрасовка? нет — посёлок в МО, НЕ Москва), «раменский район».

**Ловушки regex:** «истр» ловит «регистрация» — брать только город Истра с границей
слова; субстрока «коломен» ловит метро Коломенская; «дубн» ловит улицу Дубнинская.
**Считать гео по ТЕКУЩЕЙ `phrase`** — читателю продаётся она; `phrase_original_synth`
осмысленна как маркер замены текущего раунда, но НЕ как объект классификации
(сверка по исходникам прошлых раундов даёт фантомные миксы из уже исправленных узлов).
Перед починкой каждого помеченного узла читать ПОЛНУЮ фразу: половина срабатываний
грубого классификатора — ложняки (обрезанные при печати хвосты скрывают совпадение
слов с веткой; метро-омонимы). Легальный микс: JTBD ветки сам про
«Москва или Подмосковье» (сравнение географий) — не чинить.

**Лечение:** миноритарный гео-узел (меньшинство в ветке) менять на фразу ядра того же
направления/стадии без чужого гео; замены нет → разворот ствола/листа по JTBD (ветка
про Долгопрудный = МО-ствол, не московский); иначе синт-помета с geo_note. Если узел
двойная Москва+МО в одной фразе («москва и область») — легально, класс both.

## 2. Смена JTBD-намерения внутри ветки

Намерения: buy (куп/покупк/приобрет), sell (продаж/продат), rent_in (снять/найм),
rent_out (сдать/арендодател). Конфликт-пары: buy↔sell, rent_in↔rent_out, buy↔rent_in,
sell↔rent_out.

**Обязательные исключения ложных срабатываний:**
- «договор купли продажи», «купля продажа» — ОДИН юридический термин сделки, вырезать
  regex`ом перед классификацией (заменить на «сделка»).
- Покупательское JTBD с риском «продали арестованную» — seller-упоминание как
  риск-сценарий не меняет намерение читателя; проверять узел по leaf/jtbd ветки.
- Синт-заголовки («Синтез:», «[SYNTH]») не считать вообще — их фраза служебная.

**Лечение:** доминирующее намерение = частое в ветке; миноритарный узел менять на
корпус-фразу того же намерения (bucket направление+стадия, word-overlap ≥1 с исходной).

## 3. Развилка guide|service

- `fork` отсутствует → добавить по направлению ветки (таблица GUIDE_MAP в скрипте).
- `guide_branch` ≠ направлению: чинить, НО «проверка» в sell/buy-ветке допускает
  buy-гайд (§1: проверка — часть безопасной покупки); менять только при явной чужой
  связке.
- Directions чинить от нормализованных имён (self_kupit→buy, self_prodat→sell,
  СНЯТЬ (self_snyat)→let, rent_out→сдать; «ПРОВЕРКА»-направление → buy-гайд).

## 4. TOFU у горячего листа

Первый узел BOFU (или `leaf_type=hot`) ⇒ ни один узел ветки не может быть TOFU
(§1.2n: горячий путь без intro). Лечение: TOFU-узлы hot-ветки → MOFU (не удалять,
если длина пути после удаления уйдёт <3).

## 5. Ствол не шире листьев по count

`trunk.count <= max(leaf.count)` (count брать из узла, фолбэк — ядро по нижней
регистровой фразе) ⇒ ствол не «шире спроса». Лечение: swap на корпусную фразу того же
направления с count > max_leaf (мин. порог через min_count в кандидатах). Нет замены ⇒
снять count со ствола + запись в synth_reason (формат гейта это легализует).

## 6. Дубли chain_id на входе

Собранный ALL_CHAINS может иметь 75+ одинаковых chain_id (разные волны, один id).
Аудит по id теряет ветки при `{chain_id: ...}`-словаре. Проверять
`len(set(ids)) vs len(ids)` ДО первого шага; дубли занумеровать (#2) и держать
раздельно до финала (решение владельца по v2: склейка последних — потеря).

## Порядок прогонов (проверено в v3, 1189 веток, 3136→0 ошибок)

```
BASE_INPUT.json (копия исходника; исходник не трогать, sha256 контролировать)
→ repair_round0.py  нормализация стадий + G12 волновые блоки + хвосты + пустые поля карточек
→ repair_round1.py  G7→synthetic, G8 padding ≥60, G4 clamp, G3 links, cold→5 (синт mid/leaf/trunk)
→ repair_round2.py  G1 замены из ядра, флаги синт (source/phrase startswith 'синтез'), links
→ repair_round3.py  оставшиеся G1: конкретизация вниз в лист + замена звена (ядро/синт)
→ конвертер → гейт → семантическая батарея (гео, jtbd, fork, hot-tofu, trunk-count)
→ ручные фиксы остатков поштучно (НЕ батчить вслепую — половина срабатываний ложняки
  классификатора, см. ловушки гео выше; округлять доверием после чтения полных фраз)
→ финальный гейт + батарея → MERGED_..._GREEN.json + копия ALL_CHAINS_FINAL_vN_GREEN.json
```

Правило итераций: 3 прохода — стоп, эскалация владельцу. Каждый раунд пишет новый
файл версии и лог гейта `GATE_R<k>_raw.txt` — не перезаписывать.
