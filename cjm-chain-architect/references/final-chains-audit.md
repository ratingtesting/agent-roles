# Финальный аудит и сборка ALL_CHAINS.json

Когда рой (или несколько роёв) доехал `done`, перед сборкой единого итогового JSON выполнить
рекурсивный аудит полноты. Это ответ на требование владельца «докажи, что ничего не забыл».

## 0. Перед подсчётом полей — ДАМП одного узла целиком, не угадывать layout

Прежде чем писать скрипт «пустых полей», распечатать `json.dumps(node, indent=1)` для 2–3 узлов
свежей волны: поля кочуют между уровнями (`tail` на узле, `stage` внутри `card`, `synthetic` то
на узле то в `source`), и подсчёт «по памяти» даёт ложные массовые дефекты (было: «228 без хвоста»,
«22 пустых stage», «0 route» — из-за поиска поля не на том уровне; реальные дефекты: 7).
Системные дефекты шаблона воркера фиксировать ОДНИМ правилом-строкой для финального program-fix
(пример r7: `route` пуст у всех узлов — заполняется из `fork` цепочки; цепочки-дроблёнки по 1–2
листа вместо ветки 5+ — правка уровня задания/объединения, не контента).

## 1. Собрать ВСЕ chains.json РЕКУРСИВНО, а не по списку известных волн

```python
import glob, os
ch = r'C:/Projects/_master-1000-articles/wordstat-collector/06_Рой6_Этап11_CJM/11_cjm_chains'
files = [f for f in glob.glob(ch + '/**/chains.json', recursive=True)
         if 'node_modules' not in f]
```

- **Почему рекурсивно:** волн больше, чем ты помнишь. В этом проекте фактически: `wave1` (старая),
  `wave1full`, `wave2`, `wave2b`, `rebuild`, `wave3c`, `wave4` и `RETURNED_c2_проверка`.
  Аудит по фиксированному списку волн даёт 395–396 файлов; рекурсивный — 401. Расхождение
  = пропущенные цепочки. Список волн НЕ источник истины — файлы на диске источник.

## 2. Посчитать полноту ПОПОЛЕВО на каждом узле

Структура узла (проверено по всем волнам): `card` (СЛОВАРЬ с восьмью полями) + `transition_to_next`
+ `tail` + `cjm_stage` + `cluster_20` + `role`. НЕ `node.card.transition_to_next` — переход лежит
на уровне узла рядом с `card`, не внутри `card`.

```python
CARD = ['thought','emotion','objection','barrier','pain','info_sought','content_angle']
# для каждого узла: card есть?; каждое поле отсутствует/пусто?; transition_to_next?; tail?
```

**Устойчивый факт:** `thought`, `info_sought`, `content_angle` заполнены у ~100 % узлов.
Пустыми возвращаются ТОЛЬКО `emotion`/`objection`/`barrier`/`pain` — это четыре эмоционально-
поведенческих поля, которые генерятся нестабильно. Считать именно их по каждой волне
(`Counter` по `wave`), чтобы знать, где дыры, а не только сколько их всего.

## 3. `transition_to_next` отсутствует у стволов — это норма, не дыра

`trunk` — финальная статья цепочки, у него по дизайну нет «следующего шага» → отсутствие
`transition_to_next` у `role=trunk` НЕ дефект. Отсутствие у leaf/mid — дефект. Считать пропуски
переходов ПО РОЛЯМ, иначе стволы зашумляют отчёт и провоцируют ложный «рой неполон».

## 4. Заполнить пустые эмоциональные поля субагентами, ключ = (файл, chain_id, nidx)

Порядок:
1. Выписать все узлы, где `emotion`/`objection`/`barrier`/`pain` пусто, с контекстом:
   `wave, file, chain_id, nidx, phrase, role, cjm_stage, cluster_20, thought, info_sought,
   content_angle, missing[]`.
2. Разбить на батчи ~90 узлов; по одному субагенту на батч, параллельно.
3. Субагенту: читать свой батч, для каждого `missing` поля написать 1 фразу (8–25 слов, на
   русском, конкретную под данный поисковый запрос и стадию воронки). Писать ТОЛЬКО
   недостающие поля, не трогать заполненные. Результат — отдельный JSON на батч:
   `[{wave, file, chain_id, nidx, node_idx, fields:{emotion?/objection?/barrier?/pain?}}]`.
4. Применить обратно по ключу `(file, chain_id, nidx)`, найдя узел в `chains[].nodes[nidx]`.
5. Перепрогнать п.2 — ноль пустых по четырём полям — ТОЛЬКО тогда «полнота доказана».

## 5. Отчёт полноты — таблицей, не «я всё проверил»

Доказательство — это числовая таблица, а не заверение:

| поле | заполнено / всего |
|---|---|
| thought | N/N (100 %) |
| transition_to_next | N/N (100 % кроме trunk) |

плюс разбивка пустых по волнам. Прогон `cjm_gate.py` (G10 = «8 полей заполнены») поверх
собранного ALL_CHAINS — то же требование, машиной, чтобы владелец не верил на слово.

## 6. Прогон настоящего cjm_gate.py поверх MERGED/ALL_CHAINS

Итоговый JSON роя (`{chains:[...]}`) гейтом **не читается напрямую**: `cjm_gate.py` ждёт
верхний уровень — dict `{имя_ветки: {leaves, mid, trunk, findings, recommendations, plan}}`.
Перед прогоном конвертировать:

| поле MERGED (узел) | поле входа гейта |
|---|---|
| `nodes[]` c `role=leaf / mid / trunk` | `leaves[]` / `mid[]` / `trunk` |
| `transition_to_next` | `link` |
| `cjm_stage` (TOFU/MOFU/BOFU) | `stage_num` (1/2/3) |
| `synth_reason` | `_syn` (гейт требует ≥60 символов для mid-синтеза в тонкой ветке) |
| `role` | `tag` |
| `card.{thought,emotion,...}` и `tail` | поднять на уровень узла — гейт читает поля узла, не вложенный `card` |
| `findings/recommendations/plan` цепочки | те же ключи ветки (G12) |

Корпус для G7: у гейта зашит путь `../../funnel_v3_ALL__magnet_v2.csv` относительно `scripts/`.
Если файла нет — скопировать гейт рядом с активным корпусом проекта и подменить `CORPUS`,
НЕ правя скилл. После запуска сверить шапку: «корпус N фраз», а не «НЕ ЗАГРУЖЕН» (пустой
корпус = G7 молча пропущен).

**Числовые поля приводить к int перед сравнениями** — в волнах `count` встречается строкой;
`trunk_count <= max(leaf_counts)` падает TypeError на смешении str/int.

**Перед merge проверять уникальность chain_id.** В итоговых сборках роя дубли id штатны
(в проекте: 516 цепочек на 423 уникальных id); dict-merge по id молча перезаписывает
предыдущую цепочку — потеря не видна ни в логе, ни в гейте. Дубли → уникализировать
(`id#2`) или схлопывать явно, с записью в отчёт.

**Repair-скрипт обязан писать результат обратно в chain.** Типовая ошибка: правки
накапливаются в локальном отсортированном списке узлов, а `chain["nodes"]` не
переприсваивается — скрипт рапортует «исправлено N», на диске ничего не меняется.
После каждого repair-прохода перечитать выходной файл и пересчитать метрики, а не верить
счётчику скрипта. Отдельная ловушка: при reader_len < 3 синтетические mid добавляются
в список, но если ствол отсутствует — depth некуда привязать, узел теряется при
пересборке; после добавления перечитывать leaves/mids/trunks из фактического `nodes`.

**Синтетический ствол не чинится фейковым count.** Присваивать `count=99999`, чтобы пройти
числовую проверку «ствол шире листа», — подлог гейта: правила ширины существуют ради смысла.
Синтез помечается `synthetic=true` + обоснование ≥60 символов; если гейт не умеет exempt'ить
синтетику — это баг гейта, фиксируется владельцу, а не обходится константой.

**Порядок честной приёмки:** конвертер → настоящий гейт → разбор ошибок по правилам
(G1..G12) → план от дешёвого к дорогому (механика скриптом → решения владельца → LLM-правки)
→ вопросы-блокерЫ владельцу (конфликт G2/§1.2n, судьба фраз вне корпуса) → только потом
исправления. Объявлять цифры GREEN только из вывода канонического гейта.

## 7. Три раунда починки до GREEN по каноническому гейту (проверено 11.10.2026: 575 → 211 → 15 → 0)

Последовательность, которая сходится за 3 прохода (каждый = скрипт + конвертер + гейт):

**Раунд 1 — механика без смысла (дешёвое):**
- G7: несинтетические фразы вне ядра → `synthetic=true` + обоснование ≥60 симв. (решение
  владельца — вариант «а»); флаг ставить и когда `source='synthetic'`, а `synthetic=None` —
  гейт читает ФЛАГ, не source.
- G8: короткие `synth_reason` у mid → дописать до ≥60 симв. (проверять len, не наличие).
- G4: стадии mid+trunk привести к монотонности (clamping вверх по TOFU=1/MOFU=2/BOFU=3).
- G3: пустые `transition_to_next` → сгенерировать связку «от X — к Y» по content_angle.
- G2: cold-цепочки добить синт-mid до 5; нет листа → синт лист TOFU; нет ствола → синт ствол
  BOFU. Hot (лист BOFU) не трогать — после патча гейта они 3–5 законны.
- Патч гейта (G2 hot, темы из leaf_phrase+jtbd, G1b из объявленной темы) — копия `gate_patched.py`
  в папке проекта, рядом с активным корпусом.

**Раунд 2 — G1 пакетом, замена из ядра:** для каждого mid с чужой конкретизацией искать
кандидата в bucket `(v6_direction, стадия)` ядра: без чужих классов, без подтипов листьев,
пересечение слов со старой фразой ≥1, count>0, не занят в цепи; заменить + пересчитать tail
(«фраза · 2027») и content_angle. Направление цепочки выводить из direction/jtbd, а при
пусто — из фразы листа (куп/прода/сним/сдат/провер). Направление в ядре — ВЕРХНИМ РЕГИСТРОМ
(`ПОКУПКА/ПРОДАЖА/СНЯТЬ/СДАТЬ/ПРОВЕРКА`); `direction` в сборках роя — нижний (`self_kupit`) —
ключи bucket не сойдутся без нормализации.

**Раунд 3 — упрямые G1: конкретизация ВНИЗ, звено ЗАМЕНИТЬ** (§1.2f канон): если шире фразы
в ядре нет — опустить offending mid в `role=leaf` (мультилист легален), на его позицию
поставить общее звено (ядро той же стадии без чужих классов или синт с обоснованием ≥60).
После перестройки ролей — пересортировка `depth` (leaf→mid→trunk) и повторный clamp G4.

**После GREEN:** предупреждения G5/G6 (не блокируют) — перед докладом владельцу разложить по
единицам реальной работы (§9). «Основной источник G6 — [SYNTH]-стволы» НЕ означает «работа
переделывается»: каркас веток целый (листья, звенья, карточки, развилки валидны), не хватает
только заголовка — это детерминированный раунд переименования (§9), а не LLM-переделка.

**Канонический гейт НЕ сравнивает count** (G5 меряет длину фраз по словам и пересечения).`count=99999`
синтетическому стволу не нужен для GREEN — это подлог, оставшийся от самописного inline-гейта;
у синтеза `count=null`. Проверять это нечем, кроме как глазами на выходных JSON.

## 8. Переаудит НОВОЙ версии итоговой сборки (проверено 12.10.2026 на 1189 ветках, волны 1–7: 3136 → 25 → 1 → 0)

Когда владелец приносит свежий ALL_CHAINS_vN.json (старые волны + новые), конвейер round0→3
перезапускается ЦЕЛИКОМ с round 0. Правила, которые спасли этот прогон:

1. **Нормализация стадий-словарей — шаг №0, до всех раундов.** Новые волны несут `cjm_stage`
   человекочитаемым словарём: `"4 · DECISION · BOFU · «ВЫБИРАЮ ОБЪЕКТ...»"`, а не TOFU/MOFU/BOFU.
   Маппинг: токен внутри строки (`BOFU|DECISION→BOFU`, `TOFU|AWARENESS|PROBLEM→TOFU`,
   `MOFU|SOLUTIONS|COMPARISON|CONSIDERATION→MOFU`).round1 зависит от этого в трёх местах:
   hot-детект для G2 (`leaf.cjm_stage == BOFU`), clamp G4 (парсит только TOFU/MOFU/BOFU),
   bucket-подбор в round2 (стадия из ядра). **Патчить стадии ПОСЛЕ rounds 1–3 — гарантированный
   регресс**: в проекте поздний patch стадий вернул 3136 ошибок (round1 к тому моменту уже бил
   синт-mid под «холодные» BOFU-ветки). Любая семаantica изменения round 0 ⇒ перепрогон всей цепи
   от round 0, а не латание выходов.
2. **Конвертер параметризовать env-ами `CVT_IN`/`CVT_OUT`** (один скрипт на все версии файла).
   Жёстко вшитый путь входа — ловушка: гейт молча прогоняется на СТАРОМ файле, цифры не меняются,
   и это выглядит как «починка не помогла». **Если вывод гейта побайтово совпал с прошлым прогоном —
   сначала проверь, какой файл реально читался** (печатать `version` входа в отчёт конвертера),
   а не ищи ошибку в repair-скрипте.
3. **G7 — сверка корпуса РЕГИСТРОНЕЗАВИСИМАЯ с обеих сторон.** Ядро всё в нижнем регистре;
   фразы новых волн содержат прописные (`купить квартиру в москве Люблинский парк`) → ложные
   617 ошибок G7 на пустом месте. `.strip().lower()` при загрузке корпуса И при проверке узла.
4. **G12 волновых блоков (§1.5) на волнах без них — заполнять скриптом, не LLM.** Блоки
   findings/recommendations/plan — волновый реестр (число цепочек, развилки, доля синтетики),
   один на волну; генерится детерминированно из самих цепочек. LLM на это тратить нечем —
   это канцелярия гейта, а не смысл. В проекте так закрыто 2298 из 3136 ошибок одним проходом.
5. **G9 «два года в хвосте» на новых волнах** — год сидит ВНУТРИ angle-текста до разделителя
   (`«...в Москве в 2026: как купить... · 2027»`), а не в самом хвосте. Лечится удалением
   токена `20\d\d` из головы строки, хвостовое ` · 2027` остаётся; проверять оба держателя —
   `node.tail` и `card.tail`.
6. **Целостность исходника и версионирование — часть приёмки.** Владелец каждый аудит спрашивает:
   «итоговый json доделан? версионирование? исходник на месте?». Ответ — фактами: sha256 исходника
   до и после (он read-only, все записи — только в `audit_vN/`), таблица версий промежуточных
   файлов с траекторией ошибок гейта (3136→25→1→0), финальный файл с полем `version`.
   Итоговые сборки роя часто НЕ закоммичены в git — класть резервную копию исходника
   (`BACKUP_ORIGINAL_*`) внутрь папки аудита, хеш сверять `sha256sum`.
7. **Мелкие поля-фолбэки round 0**: пустые `card.emotion` (генерятся нестабильно — см. §2),
   хвосты без года, пустые `transition_to_next` у листов — закрывать шаблонными значениями
   до раундов; это канцелярия G10/G9/G3, LLM-работы не требует.

## 9. После GREEN: разбор предупреждений числами и читаемые заголовки вместо плацехолдеров

1. **Никогда не оценивать владельцу объём «переделки» без скриптового подсчёта.** Число в
   докладе — утверждение: сначала прогон классификации, потом речь. Разложение G5/G6:
   - **ложные** — эвристика G6/G5 меряет буквальное пересечение слов ствола и последнего звена;
     если ствол пересекается со словами JTBD/листьев ветки, ветка цела и переделывать нечего
     (проверять пересечением `[а-яё]{5,}` множеств ствол vs листья+jtbd+leaf_phrase);
   - **требуют глаз** — стволы из корпуса без какой-либо словесной связи с веткой (единицы-десятки);
   - **синт-стволы** (`[SYNTH]`/`Синтез:`) — каркас валиден, отсутствует только заголовок →
     пункт 2. Формула доклада: «из M предупреждений N ложные, K на просмотр, S переименовать»,
     а не «большая часть работы переделывается».
2. **Переименование служебных фраз `[SYNTH]`/`Синтез:` в читаемые заголовки — отдельный
   детерминированный раунд после GREEN.** Источник заголовка: `card.content_angle` звена
   (счищая хвост-суффикс направления); нет — шаблон по направлению цепочки для ствола
   («покупка/продажа/аренда/сдача…: полный безопасный маршрут сделки»), листу — «: с чего начать»,
   mid — angle или общий шаг выбора/проверки. Сохранять `phrase_original_synth` (старый
   плейсхолдер), флаг `synthetic` и обоснование НЕ снимать: фраза по-прежнему вне корпуса,
   G7 это учитывает. `tail` пересчитать под новый заголовок в обоих держателях (node.tail, card.tail).
3. **Массовое переименование даёт два регресса — закрывать тем же циклом «скрипт → конвертер →
   гейт», не объявлять готовность на глаз:**
   - **G11 дубли**: шаблонные заголовки повторяются внутри ветки → уникализировать
     детерминированно: первый повтор — суффикс ` · <chain_id>`, коллизия и с ним — ` шаг <depth>`.
   - **G1 в новых заголовках**: в angle звена просочилось слово чужого класса
     («перепланировка», «ипотека», «метро»…) — заменять слово на обобщение («состояние
     объекта», «кредитные условия», «транспорт») только у mid-ролей и только если класс
     отсутствует в темах ветки (листья + leaf_phrase + jtbd); заодно чистить пунктуацию
     после вырезания (`,,`, висячие запятые).
4. **Критерий финальной приёмки после раундов заголовков:** гейт GREEN; плацехолдер-фраз 0 —
   проверка `(phrase).strip().startswith('[SYNTH]') or phrase.lower().strip().startswith('синтез')`
   по всем узлам всех веток; в JSON — `version` + статистика раундов; копия результата в корень
   проекта с суффиксом `_GREEN`, исходник остаётся read-only (sha256 до/после — см. §8 п.6).
   Дальше файл готов как вход роя написания статей; 40-ish «на просмотр» стволов — отдельный
   короткий список владельцу, не блокер.

## 10. Фиксация канона в ROADMAP: пути под проверкой, команды под прогоном

Готовность конвейера фиксируется разделом ROADMAP проекта (единый источник правды владельца),
но запись в ROADMAP без проверки ссылок — отдельный дефект-класс (проверено вопросом
владельца «из роадмапа есть ссылки на файлы?»):
- **каждый путь** в разделе — проверить существованием по полному пути от папки ROADMAP.md
