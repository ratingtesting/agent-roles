# Kanban Swarm Orchestration (Hermes native kanban)

Пётр запускает рои агентов («Proof Pack») через нативный Hermes Kanban:
каждая карточка-документ = воркер в профиле app, волны связываются через `--parent`,
диспетчер (в gateway) сам продвигает todo→ready и спавнит воркеров. Оркестратор НЕ пишет
промпты каждому агенту вручную — только наблюдает и вмешивается при блоках.

## Когда использовать
- Задача: «рой агентов пишет пачку документов/архитектуру до кода»
- Управление волнами зависимых карточек (Vision → Product → Economy → …)
- Любая работа с `hermes kanban` (boards, create, link, dispatch, daemon)

## Основные команды
```bash
# board (изолированный, на профиль)
hermes --profile app kanban boards create <slug> --name "Name" --icon 🐝 --switch
hermes --profile app kanban init

# карточка с зависимостью-родителем и воркспейсом в папке проекта
hermes --profile app kanban --board <slug> create "Title" --assignee app \
  --workspace "dir:C:\path\to\project" --parent <parent_id> --max-retries 3 \
  --created-by founder --json --body "..."
# id новой карточки парсить из --json (python -c "import sys,json;print(json.load(sys.stdin).get('id',''))")

# линковка пост-фактум: ПОЗИЦИОННЫЕ аргументы, НЕ флаг --parent
# (`link <child> --parent <p>` падает с usage-ошибкой — проверено 2026-08-07)
hermes --profile app kanban --board <slug> link <parent_id> <child_id>
hermes --profile app kanban --board <slug> comment <id> "текст"
hermes --profile app kanban --board <slug> log <id>      # лог воркера
hermes --profile app kanban --board <slug> stats         # статусы + assignees
hermes --profile app kanban --board <slug> dispatch      # ручной тик диспетчера
```

## Критические питфоллы (проверено на Windows/MSYS)

1. **`--skill` (kanban create) и `-s` (chat) НЕ резолвят скиллы в воркере.**
   Воркер падает: `Error: Unknown skill(s): <name>` — даже если скилл виден в
   `hermes --profile app skills list` и есть на диске. Обход: НЕ передавать `--skill`,
   а вставлять в `--body` карточки строку
   `## РОЛЬ\nПервым делом вызови skill_view(name='<skill>') и работай строго в этой роли.`

2. **Диспетчер живёт только в gateway.** `hermes kanban daemon` DEPRECATED.
   Без запущенного gateway задачи остаются в `ready` навсегда. Поднять:
   `hermes --profile app gateway run` (background, long-lived). Тихо падает при
   старте, если `platforms.api_server.port` занят другим профилем (default держит 8642):
   `hermes --profile app config set platforms.api_server.port 8643` → перезапуск.
   Проверка: `hermes --profile app gateway status`.

3. **`--priority` принимает int (0-9), НЕ строку `P1`** — иначе `invalid int value`.

4. **RACE: карточка без `--parent` уходит в работу НЕМЕДЛЕННО.** Диспетчер тикает каждые 60с
   и хватает всё, что в `ready`. Если создать финальную карточку-агрегатор, а зависимости
   навесить следующей командой, воркер стартует на пустых входных данных (проверено 2026-08-07:
   карточка Founder Gate ушла в `running` до линковки). Лечение — либо сразу `--parent
   <первый_родитель>` при создании и `link` для остальных, либо после линковки:
   ```bash
   hermes --profile app kanban --board <slug> reclaim <id>   # снять claim с running
   hermes --profile app kanban --board <slug> block <id>     # заморозить до готовности волны
   hermes --profile app kanban --board <slug> unblock <id>   # разморозить ВРУЧНУЮ
   ```
   `block` НЕ снимается автоматически по завершении родителей — разблокировать обязан оркестратор.

5. **Оркестратор ОТСЛЕЖИВАЕТ рой сам, а не по просьбе.** Пётр формулирует прямо: «Ты оркестратор,
   ты должен смотреть готовность». Сразу после запуска волны поднимать фоновый монитор, а не
   дёргать `list` вразнобой. Пётр хочет ВИДЕТЬ рой: у каждого агента иконка/лицо, живая строка
   «чем занят сейчас», размеры файлов результата. Готовый дашборд —
   `templates/swarm_monitor.py` + `templates/swarm_dashboard.html`, открывать через `open_preview`.
   Диагностика зависшего воркера: `kanban log <id> | tail -25` (`runs <id>` даёт только elapsed).
   `log` на длинном воркере не укладывается в 60с — вызывать `timeout 50 hermes ... log <id>`.
   Долгое молчание при чтении большого корпуса — норма: воркер читает файлы пачками,
   артефакты пишет в конце прохода. Признак жизни — свежие строки в логе, не наличие файлов.

## Мониторинг роя: три грубых pitfall'а (проверено 2026-08-07, Review Gate)

1. **Пустой вывод `kanban list` ≠ «всё done» — частая причина ложного SWARM_COMPLETE.**
   При занятом канале (воркер читает большой корпус) CLI-вызовы возвращают пустоту/таймаут.
   Watch-скрипт вида `LIST=$(timeout 45 hermes ... list); if ! grep -qE 'running|todo|blocked'
   <<<"$LIST"; then SWARM_COMPLETE` на пустой переменной завершится ложно, хотя воркер жив.
   Защита: пусто, `LIST` = ошибка → повтор тика, не завершение; статусы брать из list +
   наличие целевых файлов. Второй прогон это подтвердил: `watch` скоммунил «done», `list`
   снаружи — 7 карточек живы.

2. **`hermes kanban log` медленный (40-60с), когда воркер нагружает канал.** Не вызывать его
   в том же цикле, что отдаёт `/api` дашборда — страница замирает. Развязка:
   быстрый цикл (`list` + размеры файлов, обновляет кэш STATE каждые 15с) и медленный
   (НЕ пишет STATE из лога воркера, каждые 20-30с). `/api` читает только кэш, субпроцессы
   не вызывает (проверено: do_GET чист от subprocess). Если `kanban log` не вернулся за
   таймаут — не паниковать, фоновый процесс жив.

3-b. **Разбор лога воркера: НЕ срезать маркеры рамки `╭╰`, чистить ANSI отдельно.**
   Строки лога обёрнуты в `╭─ Hermes ─╮ … ╰──╯`. Убрав `^[┊╭╰│─\s]+` одним классом,
   потёр служебные `╭╰` → рамка переставала распознаваться, а если их оставить как есть —
   рамка попадала в текст. Правильный `_clean`:
   ```python
   s = re.sub(r"\x1b\[[0-9;]*m", "", s)          # ANSI
   s = re.sub(r"\s+", " ", s)
   s = re.sub(r"^[┊│─\s]+", "", s).strip()       # НЕ трогаем ╭╰ — маркеры рамки
   ```
   Извлекать в активность СУЩЕСТВЕННОЕ сообщение агента (внутри рамки), а НЕ служебную
   рамочную строку и НЕ палочку тулколла (`read_file …`). Возвращать отдельно `{line, frame}`
   — дашборд рисует рамку вокруг своей копии, не вставляя сырой текст рамки.

3-d. **Лицо агента (эмодзи) дублировать в ОБЕИХ ветках JS-рендера.** Ветка с рамкой
   (`if (l.frame)`) легко теряет `${l.face}` — пользователь замечает: «раньше с пиктограммой,
   теперь без». Рамка рисуется своей строкой `╭─ ${l.face} ${l.who} ─ …╰─`, а обычная ветка
   тоже содержит `${l.face}` в своём шаблоне. Иконка — часть ожидаемого вида карточки, а не
   украшение; её пропажа = жалоба пользователя, а не косметика (проверено 2026-08-07).

4. **Симптом «агрегатор ждёт, хотя все родители done» = забытый вручную `block`.**
   Если карточку-агрегатор блокировали руками (RACE-лечение из п.4 выше), `block` НЕ снимается
   автоматически по завершении родителей — оркестратор обязан `unblock` вручную. Диагностика:
   `kanban list` показывает все родители ✓, а агрегатор ⊘ blocked — значит забыли разблокировать,
   а не «рой что-то ждёт». (Проверено 2026-08-07: Founder Gate висел в blocked при A+B1..B5 done.)

3-c. **Верификация watch/monitor-скриптов ad-hoc, но БЕЗ бесконечного цикла в главном потоке.**
   Тестируешь `poll_activity()` в синхронном assert-скрипте → `while True: sleep(20)` не
   выходит → таймаут 300с. Проверять либо статически по AST-исходникам (`do_GET` чист от
   subprocess; `poll` зовёт `list`, не `log`, и т.п.), либо выносить внутренний цикл в
   однопроходную функцию `parse_one(lines)` и тестировать её. tempfile-скрипт писать в
   `tempfile.gettempdir()`, после прогона удалять.

3. **Разбор `kanban create --json`:** `id` карточки — строка вида `t_<hex>`, НЕ число
   (регэксп `"id":\s*(\d+)` не сматчится — карточка при этом создаётся). `--json` печатает
   префикс + JSON-блок, а не чистый JSON — парсить от первой `[`/`{` (или `json_parse`).
   Сверять по `kanban list`, а не доверять регэкспу из stdout.

6. **Пересоздание карточек**: если надо пересоздать, сначала `reclaim <id>` (снять
   claim с running), затем `archive <id>`. Иначе старые воркеры продолжат писать файлы.

7. **MSYS + имена файлов с пробелами**: `for f in $(find ...)` ломается на пробелах —
   использовать `find ... -print0 | while IFS= read -r -d '' f`. Backtick-кавычки в
   grep-паттернах тоже ломают bash-строку — предпочитать одинарные кавычки или Python.

8. **Аудит-гейт после завершения волн (оркестратор обязан)**:
   - сверить структуру файлов против целевой из Brief/манифеста (часто выпадают целые
     файлы — в этой сессии не были заведены `05_Design/Design System.md` + `Wireframes.md`);
   - проверить обязательные разделы каждого документа (grep заголовков `^#{1,2}`);
   - прогнать поиск заглушек: `grep -rniE "TODO|FIXME|lorem|TBD" --include="*.md" .`;
   - битые относительные ссылки — Python-скриптом (см. scripts/check_md_links.py);
   - НЕ удалять незнакомые файлы без подтверждения: `AGENT_TEMPLATE.md` оказался быть
     личным файлом Петра из другого чата — спрашивать/проверять происхождение.
   - **Если артефакт результата испорчен/сжат агентом «восстановившим по памяти»** и git
     стартовал уже ПОСЛЕ поломки (git-коммит тоже содержит битый текст) — НЕ пересоздавать
     руками. Восстановить дословный оригинал из полного тела `write_file` в `state.db`
     (произведший воркер, а не фиксатор). См. скилл `hermes-state-db-recovery`.

9. **Лимит итераций**: в каждой карточке писать Termination Conditions + журнал
   в `PROGRESS.md` (попытка N/3, результат, причина, следующий шаг). 3/3 ❌ →
   `kanban comment <id> "🛑 ЭСКАЛАЦИЯ: ..."` — не к Петру напрямую.

## Пакетное создание многих карточек (проверено 2026-08-07, SWARM REVIEW v2)
Когда волна = 10+ независимых карточек — создавай их **Python-драйвером**, НЕ шелл-хиредоком.
`declare -A` + многострочные `--body` ломаются на апострофах (например в `DEVIL'S ADVOCATE`) и на
`done`-parse в `for … done` (bash падает `syntax error near done`). Надёжный шаблон:
```python
for slug, role, skill in roles:                 # roles = список (slug, название, скилл-роль)
    body = f"## РОЛЬ\nskill_view(name='{skill}')…\nЖЁСТКО: НЕ править MASTER/арх. Один файл SWARM/{slug}_review.md"
    cmd = ["hermes","--profile","app","kanban","--board",BOARD,"create",f"SWARM: {role}",
           "--assignee","app","--workspace",WS,"--max-retries","3","--created-by","founder",
           "--json","--body",body]
    r = subprocess.run(cmd, capture_output=True, text=True, timeout=120)
    m = re.search(r'"id"\s*:\s*"([^"]+)"', (r.stdout or "")+(r.stderr or ""))
    ids[slug] = m.group(1) if m else None       # id = t_<hex> СТРОКА; писать в SWARM/card_ids.json
```
Синтез-карточка race-safe: создать с `--parent <первый_воркер>` (→ сразу `todo`, ждёт родителей),
остальных родителей — `link <parent> <child>` позиционно. Проверка готовности:
`kanban show <id>` → строка `parents:` со всеми id. Дашборд под новую волну: скопировать
`templates/swarm_monitor.py`, поменять `BOARD` и `FACES` (ключ = роль из title «SWARM: <РОЛЬ>»,
срез до 22 симв.), пакет файлов с `REVIEW/` → `SWARM/`; запустить фоном, `open_preview`.
Разовые скрипты оркестрации верифицировать ad-hoc (py_compile + counts + `/api` ≥ N), не test-suite.
Полный рабочий пример: `references/corpus-sharm-creation.md` в скилле `swarm-review-governance`.

## Управление и визуализация роя (проверлено 2026-08-07)

- **Модель каждому агенту — штатно, per-task override.** Диспетчер спавнит воркера с закреплённой
  моделью, действует со следующего тика:
  ```bash
  hermes --profile app kanban --board <slug> set-model <id> <model> [--provider <name>]
  hermes --profile app kanban --board <slug> set-model <id> none    # сброс override
  ```
  `--provider` обязателен только если модель не из дефолтного провайдера воркера.
  Это НЕ глобальная смена модели — только на конкретную карточку.

- **Граф зависимостей (DAG) строится из готовых данных, без отдельного трекинга.**
  `hermes kanban show <id>` возвращает поле `children:` (список id) — по нему рендерится
  иерархия (напр. A → B1..B5 → C). `kanban show <id>` даёт также body/статус/время/workspace.
  Для drill-down «что делает внутри»: `kanban log <id>` (весь лог) + `kanban runs <id>` (попытки/elapsed).

- **У Hermes есть ВСТРОЕННЫЙ дашборд канбана**, но плагин `plugins/kanban/` локально НЕ установлен
  (проверено: отсутствует и в общих, и в профиле app) — вкладка Kanban в `hermes dashboard` не работает.
  Поэтому СВОЙ `templates/swarm_monitor.py` — не дубль, а закрытие реальной потребности. Наш монитор
  остаётся read-only наблюдателем роя: единственное «пишущее» действие — `set-model` по явному клику.

- **Версионировать инструмент под GitHub отдельно**, не внутри корпуса проекта: вынести в свой
  репозиторий (`.gitignore`, README, LICENSE, RESEARCH.md-план), коммитить с версией (v0.1.0, …).
  См. скиллы `skill-repo-hygiene`, `skill-publishing-sync`.

## Повторная волна на том же корпусе (проверено 2026-08-08, MVP Consolidation Gate)

- **Не писать драйверы с нуля.** Копировать `.swarm/make_cards_v2.py` → `make_cards_w3.py`,
  `make_synthesis_v2.py`, `monitor.py` → `monitor_w3.py`. В мониторе правятся ровно два места:
  `BOARD` и словарь `FACES`. Ключ `FACES` = роль из title после `SWARM: `, усечённая до 22 символов
  (`FACES = {k[:22]: ...}`) — длинные роли писать в словаре уже усечёнными
  (`"SYNTHESIS — MVP CONSOLIDAT"`), иначе агент отрисуется дефолтным 🤖.
- **Длинный вход агентам — файлом на диске, а не в теле карточки.** Список 44 решений мастер-модели
  записан один раз в `SWARM/MASTER_DECISIONS_W3.md`, карточки ссылаются на него. Тело остаётся
  читаемым, правка списка не требует пересоздания карточек.
- **Единый блок `COMMON` в конце каждого тела**: запрет кода; перечень защищённых от правки
  документов; факт без ссылки на файл — писать «нет источника»; неподтверждённое — `VERIFY`;
  русский; ровно один выходной файл; Termination 3 → `🛑 ЭСКАЛАЦИЯ`; **выбор уровня Founder (A/B/C)
  агент не делает сам — выносит в раздел `FOUNDER DECISION REQUIRED` своего файла.**
- **Форму итогового отчёта задавать в теле синтез-карточки дословно**: шапку (`STATUS: …`) готовым
  code-блоком для копирования, затем пронумерованные разделы и обязательный финальный блок вопросов.
  Отдельной строкой: «входного файла нет или он пуст → не выдумывать, пометить пробел в отчёте».
- **Пре-флайт оркестратора**: `gateway status` (stale `gateway_state.json` после негрейсфул-стопа —
  норма) → поднять через `terminal(background=true)`, шелловый `&` тул отклоняет → чекпойнт-коммит →
  Termination Conditions в `PROGRESS.md` отдельным коммитом → доска/карточки/синтез/монитор → коммит.
- **Верификация оркестраторских скриптов — ad-hoc, во временной папке, с удалением после прогона**:
  py_compile, `len(ROLES)`, уникальность слагов и выходных файлов, отсутствие `--skill`, наличие
  `skill_view(...)` в теле, `card_ids*.json` = N+1 id `t_*`, разделы в теле синтеза. Живой пруф —
  `curl /api` монитора (12 карточек, 11 running, синтез todo). В ответе Петру: таблица проверок
  плюс явная строка «чего верификация НЕ доказывает» (качество текстов ловит аудит-гейт, не эти проверки).
- Полные детали волны: `references/consolidation-gate-wave.md`.
